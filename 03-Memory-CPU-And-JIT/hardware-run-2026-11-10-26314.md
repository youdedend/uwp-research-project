## The trigger, identified by the user (2026-11-10, same evening)

> "After the first cutscenes where I suppose to chose my character it crash when the game try to
> load my character"

The 1,225 presents = intro cutscenes + character-creation screen (smooth). The wedge/burst falls
exactly at the **character-creation → game-world load transition**: the +1.8 GiB `UWP alloc:`
buffer-cache storm = level/streaming data, and the 5× `D16Unorm 1x1x1 layers N→N+1` copy-layer
mismatches = depth/shadow textures being re-mapped for the real world (the preview scene's
mapping at `0x10d1d50000` freed id=94..98 in sequence). The historical "stalls/DEVICE_LOST after
800–1,300 presents" were this same transition. Trigger is now reproducible in principle: cold
boot → sit through intro → create/confirm character → observe the load.

## ROOT CAUSE FOUND (2026-11-10, same evening) — `vulkan_dzn.dll` NULL deref

`loader-2026_11_10-2.log.txt:2003` (printed by `xbox/platform/main.cpp`'s VEH last-chance
logger, `uwp_last_chance_logger` at `main.cpp:1622`, NATIVE FAULT print at `:1678`):

```
UNHANDLED NATIVE FAULT: code=0xc0000005 module=vulkan_dzn.dll+0x1fd79 rip=0x7ffbf210fd79 rsp=0xb301ff2a0 addr=0x150
```

**Access violation (NULL-object field read at `addr=0x150`) inside Mesa Dozen** — the
Vulkan→D3D12 translation layer — during the character-load allocation storm. Corroboration:
the same crash dump region shows `UWP thread op: tid 3388 in 'recording Vulkan commands'
(0x179=377 queued chunks, 0) for 5897 ms` (`:1975`) — the renderer thread died mid-recording;
fence `2455/2454` then never advanced (41 s), presents frozen at 1,225. The 51 lightweight
`UWP breadcrumbs (unhandled exception)` dumps earlier in the run are guest-code exceptions
passing through the same logger (`main.cpp:1629` dumps breadcrumbs before the code check at
`:1633`); the heavy dump at `:1955-2003` (thread samples + ops + breadcrumbs + FAULT line) is
the fatal-class one (code in the AV/illegal/div0/stack/assert list).

Fix-lead audit (all verified via `gh api` on `Cosmo/mesa_ai_slop_version`):
- The build pin `a76cd3c` (2026-10-21, "dzn: Skip the buffer descriptor cache for buffers whose
  ranges change") is **ahead of** the fork's published HEAD `8280496` and already contains the
  October copy/barrier fixes `7a72a16` (bufferImageHeight for layer stride of buffer/image
  copies), `199b69a` (transition barriers for depth/stencil and layer ranges), `e719904`,
  `ce02589` — so "bump the pin" does not fix this crash.
- Prime suspect is now the **interaction** around our own copy guard: `vk_runtime.cpp:103`
  `LogCopyMismatch("copy layer mismatch", …)` *skips* the copy when layer counts differ — and
  the 5 skipped D16Unorm copies at guest `0x10d1d50000` (freed id=94..98) are the exact activity
  at the freeze. A skipped copy leaving an invalid/empty image view that dzn later dereferences
  is consistent with `addr=0x150` (field of a NULL object). Not proven.
- To decode `vulkan_dzn.dll+0x1fd79` to a source line: CI run `42837339701` keeps artifacts
  `dozen-uwp` (dzn build, 1.7 MB) and `bloodborne-map-9849caf…` (1.5 MB map) — downloads are
  blocked from the agent sandbox (Azure blob), but the user can grab them from the run's
  Artifacts section in a browser.
- Zero-code repro aid: fork commit `cc9399e` added `DZN_DEBUG=d3d12` (log D3D12 debug-layer
  errors) — settable in `graphics-debug.txt` for the next run without a new build.

### DECODED 2026-11-10 (evening): the exact crash instruction, named

The `dozen-uwp` CI artifact (uploaded by the user to Google Drive) was disassembled at
`+0x1fd79` (`decode_dzn_crash.py`, capstone+pefile; full report verbatim in
`hardware-run-2026-11-10-26314-logs/decode-vulkan_dzn-crash.txt`). Result:

- **Faulting instruction** `0x1fd79: mov rcx, qword ptr [rax + 0x70]`, where
  `rax = [rdx + 0x10]` — and `addr=0x150` proves `rax == 0xE0 (224)`, garbage.
- **Function**: `dzn_image_get_copy_loc()` (`dzn_image.c`, builder at
  `dzn_image.c:438–444`; call sites `dzn_cmd_buffer.c:2611–2612` inside
  `dzn_cmd_buffer_copy_img_chunk()` — the **image-to-image texture copy** chunk path).
  Struct layout matched field-for-field against `struct dzn_image` (`dzn_private.h:1162`):
  `+0x10 base.device | +0x4c vk.format | +0x54 extent.height | +0x58 extent.depth |
  +0x98 linear.row_stride | +0xa0 desc.Dimension | +0xd8 res` — every disassembly read maps.
- **The read**: `image->vk.base.device->physical` —
  `vk_object.h:56` (`struct vk_device *device` at +0x10 of every Vulkan object) →
  `vk_device.h:116` (`physical` at `vk_device+0x70`; base 0x40 + VkAllocationCallbacks 0x30).
- **Mechanism (proven)**: a `dzn_image` with `device == 0xE0` reached the copy builder
  during the character-load texture storm → read at 0x150 → 0xC0000005 → renderer thread
  died mid-recording (loader-2 `:1975`) → fence wedge → freeze at 1,225 presents.
  Only a **freed/reused/stale image object** can carry `device == 0xE0`; the same log
  window shows the `copy layer mismatch` D16Unorm 1×1×1 layer re-maps and texture frees
  (id=94–98 @ guest `0x10d1d50000`) that tear image records down.
- **Still not proven**: whether our copy-layer-mismatch SKIP (`vk_runtime.cpp:103`)
  causes the stale record or the game's own free/re-map timing does. Deciders:
  `DZN_DEBUG=d3d12` repro run + diag-1 wedge tags + hardening the mismatch-skip path.
